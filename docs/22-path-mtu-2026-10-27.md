# Path-MTU black hole on Meta and Vercel CDN paths — 2026-10-27

Status: live host fix applied. No wire-format or `beam` binary change.

## Symptom

The Android client on mobile data could open many sites but repeatedly showed
`network changed` on some, and Instagram Reels stopped after the first buffered
part. TikTok reported an unstable network. The same failures happened with the
production client from the laptop, so they were not specific to the phone.

The clearest reproduction was `https://artificialanalysis.ai/`: DNS resolved,
TCP connected, and curl sent a TLS ClientHello, but no ServerHello arrived.
The same happened for `vercel.com`. Plain HTTP returned a small `308` response,
so this was not a routing or listener failure.

## Measurement

The production VPS has a **1460-byte path MTU** to:

- Meta/Instagram CDN `57.144.0.0/16`
- Vercel `76.76.21.0/24`

Probe with ICMP DF (`1432 + 8 ICMP + 20 IPv4 = 1460`):

```text
57.144.222.192   1432:ok   1442:fail  1472:fail
76.76.21.21      1432:ok   1442:fail  1472:fail
```

The paths advertise an MSS based on 1500 bytes, but silently drop any packet
larger than 1460 bytes and never return ICMP fragmentation-needed. The result
is a PMTU black hole: the TCP handshake and small HTTP responses work, while a
TLS ServerHello, a certificate chain, a video segment, or an Instagram JSON
response stalls until the application times out or retries.

## Fix

Add route-specific MSS clamping for the two measured prefixes:

```text
ip route replace 57.144.0.0/16 via <gateway> dev <iface> advmss 1400
ip route replace 76.76.21.0/24 via <gateway> dev <iface> advmss 1400
```

`advmss 1400` leaves 20 bytes below the observed 1460-byte path MTU. The fix is
route-specific, so normal 1500-byte destinations keep their full MSS; there is
no global throughput cost. `net.ipv4.tcp_mtu_probing` stays **0**.

`deploy/beam-mtu.sh` detects the default IPv4 gateway and interface and applies
both routes. `deploy/beam-mtu.service` runs it after `network-online.target`;
`deploy/bootstrap.sh` installs and enables both files.

## Verification

Before the clamp, from the production host:

```text
curl https://artificialanalysis.ai/  -> timeout after 12 s
curl https://www.instagram.com/       -> timeout to 57.144.222.192
```

After the clamp:

```text
artificialanalysis.ai  200, 0.55 s, 1.48 MB
Instagram CDN          200, 0.60 s, 370 KB
end-to-end via tunnel  200, 1.0-1.9 s
```

The phone must reconnect the VPN (or wait for new connections) because the
MSS clamp applies to new TCP connections, not sockets already established.

## Scope and follow-up

This fixes the measured Meta `57.144.0.0/16` and Vercel `76.76.21.0/24`
prefixes. Other CDNs tested from the host (`2.x`, `23.x`, Google, Cloudflare,
Fastly) accepted 1500-byte probes. If another destination later shows the same
pattern, add its prefix to `deploy/beam-mtu.sh` only after the same DF probe;
do not enable global MSS clamping or `tcp_mtu_probing` as a first response.
