# Path-MTU black hole on Meta and Vercel CDN paths — 2026-10-27

Status: **superseded by `docs/23-target-mss-2026-10-27.md`**. The final fix is
inside beam (`TCP_MAXSEG 1400` on target sockets); the host-route workaround
described below has been removed.

This file is retained as the diagnosis and measurement history.

## Symptom

The Android client on mobile data could open many sites but repeatedly showed
`network changed` on some, and Instagram Reels stopped after the first buffered
part. TikTok reported an unstable network. The same failures happened with the
production client from the laptop, so they were not specific to the phone.

The clearest reproduction was `https://artificialanalysis.ai/`: DNS resolved,
TCP connected, and curl sent a TLS ClientHello, but no ServerHello arrived.
The same happened for `vercel.com`. Plain HTTP returned a small `308` response,
so this was not a routing or listener failure.

## Measurement

The production VPS has a **1460-byte path MTU** to:

- Meta/Instagram CDN `57.144.0.0/16`
- Vercel `76.76.21.0/24`

Probe with ICMP DF (`1432 + 8 ICMP + 20 IPv4 = 1460`):

```text
57.144.222.192   1432:ok   1442:fail  1472:fail
76.76.21.21      1432:ok   1442:fail  1472:fail
```

The paths advertise an MSS based on 1500 bytes, but silently drop any packet
larger than 1460 bytes and never return ICMP fragmentation-needed. The result
is a PMTU black hole: the TCP handshake and small HTTP responses work, while a
TLS ServerHello, a certificate chain, a video segment, or an Instagram JSON
response stalls until the application times out or retries.

`net.ipv4.tcp_mtu_probing=1` does **not** fix this direction: the dropped
packets are sent by the peer, and the peer keeps using the MSS that we
advertised in our SYN. The advertised MSS itself has to be reduced.

## Fix

Advertise a conservative MSS on the IPv4 default route:

```text
ip route replace default via <gateway> dev <iface> proto <proto> advmss 1400
```

This is global: every outbound TCP connection advertises MSS 1400, so peers on
a 1460-byte path send at most 1400 payload bytes. There is no per-prefix or
per-service list. `advmss 1400` leaves room for TCP timestamps and IP/TCP
headers. Normal 1500-byte paths continue to work with a slightly smaller
segment.

`deploy/beam-mtu.sh` detects the default IPv4 gateway, interface, and protocol,
removes any old per-prefix clamps, and applies the global setting.
`deploy/beam-mtu.service` runs it after `network-online.target`;
`deploy/bootstrap.sh` installs and enables both files.

## Verification

Before the clamp, from the production host:

```text
curl https://artificialanalysis.ai/  -> timeout after 12 s
curl https://www.instagram.com/       -> timeout to 57.144.222.192
```

After the clamp:

```text
artificialanalysis.ai  200, 0.55 s, 1.48 MB
Instagram CDN          200, 0.60 s, 370 KB
end-to-end via tunnel  200, 1.0-1.9 s
```

A 100 MB long-flow comparison against `ash-speed.hetzner.com` gave 112-144
Mbps with the global clamp and 110-115 Mbps without it, i.e. no measurable
long-flow regression. Short flows pay a small slow-start cost because the
initial window carries less data.

The phone must reconnect the VPN (or wait for new connections) because the
MSS clamp applies to new TCP connections, not sockets already established.

## Trade-off

Global `advmss 1400` reduces the maximum TCP payload from 1460 to 1400 bytes
(about 4%). It is the only setting that fixes all destinations without a
per-prefix list. If a future path is smaller than 1400, lower the value in
`beam-mtu.sh`; do not enable `tcp_mtu_probing` as a first response, because it
does not change the MSS advertised to the peer.
