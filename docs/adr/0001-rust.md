# ADR 0001: Use Rust

## Status

Accepted.

## Context

`beam` is a server-only rewrite of a narrow Xray profile: VLESS, REALITY,
Vision, TCP, and XUDP on Debian 13, x86_64, one vCPU, one user. The project must
be faster than stock Xray and must be written and maintained primarily by AI
agents.

Candidate languages were Rust, Go, C++, and Zig.

- Go would make behavioral parity easiest, but it shares the runtime and GC
  characteristics that limit stock Xray. Beating stock by a meaningful margin
  would be unlikely.
- C++ has the highest performance ceiling and direct access to BoringSSL and
  liburing, but manual memory management, undefined behavior, and build-system
  complexity are a poor fit for autonomous AI maintenance.
- Zig has a good performance ceiling but an immature TLS and networking
  ecosystem for this use case.

## Decision

Use Rust, edition 2024, with a pinned toolchain. Keep protocol and state-machine
code in safe Rust. Isolate Linux syscalls in `beam-sys`. Use BoringSSL through
the `boring` crate if the TLS spike shows a concrete advantage; otherwise use
`rustls` with `aws-lc-rs` or `ring`.

## Consequences

- Memory and concurrency safety are enforced by the compiler.
- The compiler, `clippy`, tests, and fuzz targets act as automated reviewers.
- The async data path must be designed carefully; the hot relay loop will use a
  dedicated `splice` path instead of async buffering.
- C++ libraries can still be used through narrow FFI wrappers.
- Build and dependency management stay reproducible with Cargo.
