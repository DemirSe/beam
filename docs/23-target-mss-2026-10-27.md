# Target-socket MSS clamp in beam — 2026-10-27

Status: implemented and deployed. No wire-format change. Supersedes the
host-route workaround in `docs/22-path-mtu-2026-10-27.md`.

## Problem

The production VPS has a 1460-byte path MTU to Meta/Instagram CDN
`57.144.0.0/16` and Vercel `76.76.21.0/24`, but those paths advertised a
1500-byte MSS and silently dropped larger packets. TLS ServerHellos, video
segments, and Instagram JSON responses stalled while small HTTP responses
worked. The same failure reproduced through the beam tunnel and directly from
the VPS. See `docs/22-path-mtu-2026-10-27.md` for the original measurements.

A host-wide `advmss 1400` route fixed the observed sites but applied to all
host traffic, needed a systemd oneshot, and could be lost when systemd-networkd
recreated the route. The final fix belongs in beam's target dial path.

## Change

- `beam-sys::set_tcp_maxseg` / `get_tcp_maxseg` wrap `TCP_MAXSEG`.
- `tls::server::dial` resolves the destination, creates a `TcpSocket`, sets
  `TCP_MAXSEG` while the socket is still unconnected, then connects. This is
  required for Linux to use the value both for the MSS option in the SYN and
  for the local send limit.
- A single constant, `TARGET_MSS = 1400`, applies to every beam target and
  cover connection. There is no per-prefix, per-service, nftables, or host
  route configuration.
- `TcpSocket` also gives a bounded resolve/connect deadline and preserves the
  existing IPv4/IPv6 address iteration.

On Linux, `TCP_MAXSEG 1400` produced an effective advertised MSS of 1388 in
production (`ss -tin` showed `mss:1388 advmss:1388`), leaving room for TCP
timestamps and IP/TCP headers below the 1460-byte path MTU.

## Verification

- `cargo fmt --all --check`
- `cargo clippy --workspace --all-targets -- -D warnings`
- `cargo test --workspace`: **306 tests**, all pass
  (277 beam-core + 1 stock ClientHello + 2 TLS server + 26 beam-sys).
- New test `tls::server::tests::dial_limits_target_mss_and_connects` verifies
  that `dial` connects and the resulting socket's MSS is at most 1400.
- Full-TUN lab matrix: **11/11 PASS**.
- Lab 10-repetition beam A/B, QEMU pinned, new target clamp vs old binary:
  **1993.90 vs 1979.58 Mbps**, CPU/GiB **2.936 vs 3.013**, TTFB p95
  **127.05 vs 126.82 ms**. The throughput difference is within run noise; the
  clamp did not regress the lab path.
- Production with the host route and `beam-mtu.service` removed:
  `artificialanalysis.ai` **200** in 1.3–1.9 s through the tunnel,
  Instagram CDN **200** in 1.3–1.6 s. Direct host curl to
  `artificialanalysis.ai` still times out, which is expected: only beam's
  target sockets are clamped, not unrelated host traffic.

## Scope and trade-offs

- Applies to TCP sockets opened by beam for VLESS TCP, Vision Direct, and the
  cover relay. It does not affect XUDP, legacy UDP, packetaddr, or UDP/QUIC
  traffic.
- The configured 1400 becomes 1388 payload bytes on the wire, about 5% less
  than the old 1460 path. The lab benchmark showed no measurable regression;
  short flows may pay a small extra-segment cost.
- The host's own TCP traffic is intentionally not clamped. If another host
  process needs the same workaround, it needs its own MSS policy; beam does not
  change global networking.
- The previous `beam-mtu.service`, its script, and the default-route `advmss`
  are removed from the deployment and the live host. The documentation in
  `docs/22-path-mtu-2026-10-27.md` remains as the diagnosis/history.
