# TLS Direct pipe sizing — 2026-10-27

Status: local candidate, not deployed to production. No wire-format change.

## Finding

The Vision Direct bulk path uses `splice(2)` through one pipe per direction.
The previous default was 512 KiB (`DEFAULT_PIPE_SIZE`). Profiling the local
three-VM lab showed that the TLS Direct HTTPS path is sensitive to this
capacity:

- single 128 MiB HTTPS download, 10 alternating samples, 2 GHz pinned profile:
  **966.7 → 1007.3 Mbps (+4.2%)**, median paired delta +45.4 Mbps,
  **8/10 wins**, server CPU/GiB **2.13 → 1.99 s (-6.6%)**.
- the non-TLS iperf path does not use `splice`; its official 10-repetition
  run was unchanged (1276.7 vs 1280.3 Mbps, CPU/GiB 4.957 vs 4.915, TTFB p95
  127.8 ms both).
- H3 is not affected (10 paired samples: p95 median 134.6 ms both, 6/10 wins).

## Why a naive 1 MiB default was rejected

Linux charges pipe pages against the per-user `fs.pipe-user-pages-soft`
limit, which is 16,384 pages (64 MiB) on Debian. Two 1 MiB pipes per Vision
connection consume 512 pages, so 64 concurrent HTTPS connections need
128 MiB. With the default limit, a fixed 1 MiB pipe regressed a
**64 × 8 MiB** HTTPS download from 72.35 to 69.59 MB/s (-3.8%). All requests
still returned 200, so this was a throughput regression, not a failure.

## Change

`RelayConfig::default()` uses `BEAM_PIPE_SIZE` once at startup:

| Configuration | Pipe | Reason |
|---|---:|---|
| unset (default) | **512 KiB** | Debian default pipe-page limit; preserves 64-way concurrency |
| `BEAM_PIPE_SIZE=1048576` | **1 MiB** | only valid with 256 MiB pipe-page soft limit; 120 directions fit (2 × 1 MiB × 120 = 240 MiB) |

An absent, malformed, non-power-of-two, or out-of-range value falls back to
512 KiB. The choice is read once, so a restart is required after changing it.
The code deliberately does not read `/proc/sys` at runtime: the production
unit uses `ProcSubset=pid`, which hides `/proc/sys`, and silent fallback would
make the policy environment-dependent.

The optional host tuning is:

```bash
sudo install -m 0644 deploy/99-beam-pipe.conf /etc/sysctl.d/99-beam-pipe.conf
sudo sysctl --system
sudo install -d /etc/systemd/system/beam.service.d
sudo install -m 0644 deploy/beam-pipe.conf /etc/systemd/system/beam.service.d/99-beam-pipe.conf
sudo systemctl daemon-reload
sudo systemctl restart beam
```

`bootstrap.sh` does **not** install either optional file, so a fresh deployment
keeps the conservative 512 KiB behavior and has no concurrency regression by
default.

## Verification

- `cargo fmt --all --check`
- `cargo clippy --workspace --all-targets -- -D warnings`
- `cargo test --workspace`
- `cargo test --workspace --release`
- full-TUN functional matrix: **11/11 PASS**
- 64 × 8 MiB HTTPS with the 256 MiB soft limit: **64/64 HTTP 200**, aggregate
  72.24 vs 71.35 MB/s old/new, max request time 6.52 vs 6.71 s; peak server
  RSS ~66.7 MiB, current ~7.3 MiB, `NRestarts=0`.
- 64 × 8 MiB HTTPS with the default 64 MiB soft limit and a fixed 1 MiB pipe:
  **64/64 HTTP 200**, but 69.59 vs 72.35 MB/s, which is why the adaptive
  selection is required.
- broad real-world suite: 210 normalized samples, zero probe errors; no
  functional or edge-case changes. Non-TLS HTTP/DNS/UDP and the shared-client
  limits are unchanged.

## Trade-off

The larger pipe is only selected when the host explicitly allows it. At the
120-direction splice cap it can reserve up to 240 MiB of pipe pages, still
below the 256 MiB soft limit and the service's 768 MiB `MemoryMax`; operators
who do not need the single-flow HTTPS gain should leave the Debian default.
